# SNOMED Solver Workbench

Status: Exploratory product specification. Implementation has not started. This specification originated in [`sct`](https://github.com/pacharanero/sct/blob/6384c9a2c0c39f73a66e133b2641d56f9ea92be3/spec/marimo-snomed-notebook.md) from lessons learned in a local private Data Golf workbench and now belongs to this repository. It refines the older [marimo/Jupyter idea in `sct` issue #42](https://github.com/pacharanero/sct/issues/42) without closing that broader issue.

## Problem And Product Hypothesis

`sct` makes terminology fast and local, but its CLI, MCP, GUI, and Python surfaces do not yet give a clinician and a trusted agent one place to jointly formulate a question, inspect concept sets, change a proposed rule, and see how the change affects data. Agents can generate standalone analyses faster than a person can read them. A code-only notebook can reproduce that imbalance; a visual terminology browser alone cannot show application-specific row reasoning. A SNOMED-aware marimo notebook might connect both without moving a mature solver into notebook cells.

The central interaction is: **question and rationale -> editable terminology expression -> artefact-pinned concept set -> externally supplied application rule -> bounded presentation of the change -> inspect the concepts behind the change**. A human and, where policy permits, an agent should be able to read the same source and results. This is a concept-set analysis and codelist-design surface, not a new definition of clinical truth, a patient-data store, or SNOMED content authoring. Any accepted codelist is persisted only through an explicit human action and the existing checked `sct` codelist path, never through a notebook-specific format.

## Relationship To `sct`

- The [`sct` SDK specification](https://github.com/pacharanero/sct/blob/main/spec/sdk.md) describes the shipped typed Rust engine and `sct-py` adapter. Use them for current-release lookup, lexical search, expansion, hierarchy, and provenance. Fill genuine capability gaps there rather than scraping formatted CLI output or implementing ECL again in Python. Python results are ordinary dictionaries and lists, so this repository must validate them into explicit local models rather than treating `dict[str, Any]` as a typed boundary.
- [`sct` issue #42](https://github.com/pacharanero/sct/issues/42) proposed plain SQL as an interoperability layer with marimo and Jupyter veneers, while [issue #41](https://github.com/pacharanero/sct/issues/41) tracks DuckDB integration. The first notebook slice should prove the shipped `sct-py` semantic path. A later Jupyter veneer may reuse importable adapter code, and DuckDB may bridge application data, but neither becomes a second terminology engine or the source of ECL semantics.
- [`sct` roadmap item `R38`](https://github.com/pacharanero/sct/blob/main/spec/gui.md) specifies a planned search-first clinical knowledge atlas with reusable custom elements and a pluggable terminology adapter. This notebook is a complementary write-and-test analysis surface; `R38` remains the primary browse-and-understand GUI. Prototype an embedded concept inspector against the same semantics and later assess measured reuse. Do not turn `R38` into a marimo dependency or publish a component library ahead of its existing gate.
- The [`sct` ECL specification](https://github.com/pacharanero/sct/blob/main/spec/ecl.md) documents the shipped grammar and gaps. The shared evaluator refuses grouped refinement rather than flattening it into a conjunction, so the notebook inherits that refusal and needs no separate group-rejection check. The first slice is still gated on actionable parser/evaluator diagnostics crossing the Python boundary and annotation warnings reaching a structured adapter channel rather than process stderr. It must never guess, silently broaden, or silently narrow a set.
- [`sct` roadmap item `R25`](https://github.com/pacharanero/sct/blob/main/spec/roadmap.md#larger-product-capabilities) does not yet provide module-aware point-in-time reconstruction. A current-release SDK lookup must never be labelled as an exact historical edition. Current Snapshot inactivation reasons and associations are not a chronological lifecycle, and their absence must be distinguished from history evidence not being loaded.
- Preserve `sct`'s canonical RF2 -> NDJSON -> derived SQLite path. Notebook, Python adapter, and anywidget code must not build a private RF2 import or duplicate terminology SQL. Native reads remain read-only. The [`sct` output-boundary specification](https://github.com/pacharanero/sct/blob/main/spec/output-boundaries.md) governs generated HTML, Markdown, JavaScript, and code display. [`R87`](https://github.com/pacharanero/sct/blob/main/spec/refset-discovery.md#r87-local-dataset-coverage) remains the design gate for any local dataset-coverage helper.

## Jobs And First Useful Screen

The default view is one question, not an empty data-science canvas: clinical intent and uncertainty at the top; expression and policy controls alongside a concept-set summary; aggregate effect on authorised local data below; evidence and provenance always accessible. A run is a proposal until separately accepted by its owning application. Clicking an aggregate should retain the question, filters, terminology release, application-defined strata, and reason for inspection. Human-agent sessions use synthetic data by default.

1. Search a clinical phrase with shipped lexical search, or look up a syntactically valid SCTID exactly, without losing the question. Present candidates for human selection rather than claiming ranking identifies the clinically correct concept. Show the preferred term stored in the selected database, FSN, SCTID, active status, primary release identity, and content fingerprint. A composite build records only its first source as the primary release; exact constituent releases require an external manifest, while source paths remain redacted. A semantic tag parsed from the FSN must be labelled as derived. Report locale, inactive-content policy, and refset mode as `not recorded` unless an external build manifest supplies them. Absence from an active-only database is not proof that a description was absent from the published release.
2. Write or paste ECL, validate it, then run it explicitly against the selected loaded artefact. Editing marks results stale instead of re-running an expensive expansion on every keystroke. Compare `added`, `removed`, and `unchanged` SCTIDs against a reference expression and inspect a display-bounded sample. Distinguish a display limit from the current SDK's full materialisation of `expand()`; do not claim a query deadline, cancellation, or backend result bound until those exist. Show total, returned count, truncation, primary release identity, and content fingerprint. If caching is introduced, show a cache key/status bound to expression, artefact fingerprint, options, and engine version. Expression annotation text is not authority for concept identity.
3. Move from a concept to direct parents, a limited child list, loaded inferred attribute relationships, and current Snapshot inactivation status and associations. Show multiple direct parents and disclose every limit or omitted result. Pagination, complete root routes, and group-preserving attributes require new SDK contracts and must not be simulated. Do not render a force-directed whole-ontology cloud. Show a keyboard- and touch-accessible inspector, not hover-only navigation.
4. In a later slice, test whether a proposed concept-set change affects an application's row predicate where an authorised adapter exists. Keep terminology membership, clinical interpretation, and row eligibility such as age, dates, labs, and medicines separate. Follow `R87` for encounter keys, duplicate policy, field and combined denominators, matching mode, and build provenance. Show only aggregate additions/removals and locally filtered cohorts; never treat an expansion-count change as a measured patient-answer change.
5. Review reproducibility using what can actually be known: source and reference expressions, adapter options, notebook/package and `sct` versions, release ID, canonical content and companion fingerprints, local digest of sorted result SCTIDs, and actual query invocation. Original build argv, binary/database file hashes, locale, and ingest policy are shown only when independently captured, otherwise as `not recorded`. Source and database paths are sensitive local metadata and must be redacted from exportable views. Distinguish local runs, externally submitted observations, and estimates; never infer an external result that was not observed.

### Concept Lens And Hierarchy Affordances

Render SCTIDs in result tables as selectable concept references with a short hover/focus preview of FSN, preferred term, activity, and release. Selecting one opens a persistent inspector with direct hierarchy neighbours, loaded inferred relationships, current status/associations, and membership in current/reference expressions. The same inspector should be reachable by search and keyboard. Hover over tokens inside an ECL editor is a later editor-integration or custom-widget experiment, not a capability to assume marimo provides natively. It must recognise syntactically valid ECL concept references, not arbitrary numeric strings.

A release comparison identifies every database by primary edition/release and content fingerprint and states its alignment policy instead of offering one ambiguous global `as-at` switch. A composite database claims exact constituent releases only when an external manifest records them. Keep the difference between a published module-aware edition and a naive component cutoff visible. Until `R25` exists and is independently validated, compare separately loaded artefacts or clearly labelled approximations only; never silently claim historical reconstruction.

### Decision-flag Submission Builder

The private Data Golf solver placed each adopted clinical judgement behind its own opt-in flag: never default-on, threaded through one options dictionary, and adopted only after its impact had been priced and scored. This is a concrete later shape for job 4's application adapter, not competition logic to distribute here.

A submission-builder page would list one row per registered flag: human-readable rationale, the ledger entry that adopted or rejected it if any, and a checkbox bound to the same options dictionary that the owning CLI builder threads through its preparation and answer stages. It must not maintain a notebook-local shadow registry. Toggling a checkbox recomputes only affected columns against the selected artefact and shows `added`, `removed`, and `unchanged` row counts per column. It never invents a predicted score: a candidate can show a priced envelope and, only if that exact candidate was submitted, its observed score from an append-only ledger, clearly labelled and never blended.

This addresses a recurring failure mode in which several columns are bundled into one submission to conserve a scarce quota, preventing the scored effect of each change from being decomposed afterwards. Local row-level recomputation makes every flag's effect inspectable before a slot is spent without pretending bundled score attribution is possible. Visible guardrails must include that a removed row currently carries the removed value, a lock anywhere for a concept beats a mark anywhere for that concept, and an addition cannot manufacture more true rows than the priced false-negative pool. This later slice depends on `R87` and an authorised application adapter.

## Architecture And Boundaries

```text
user / trusted agent <-> marimo notebook (question, ECL editor, inspector, aggregates)
                                  |
                     schema-validating adapter
                                  |
                       sct-py -> typed Rust SDK
                                  |
licensed RF2 -> canonical NDJSON -> derived read-only SQLite

marimo notebook -> explicit authorised application adapter
                -> least-privilege external rule runner -> aggregate result
```

Use marimo's Python-file notebook format for diffable source. Generated output is not embedded in that source, but static HTML, Markdown, output-bearing IPYNB/PDF/PNG, executed WebAssembly exports, and session snapshots are persisted artefacts governed separately. The first prototype can use a code editor, explicit run button, search, and tables whose data is limited before construction. Table pagination is presentation, not a query bound, and downloads must be disabled wherever persistence is forbidden. Use one serial `sct-py.Snomed` session per query worker; do not concurrently share its synchronous connection. Use a small fully local custom widget only if a persistent concept inspector or editor-token interaction cannot be composed from standard controls. Any reusable atlas element receives schema-validated data through an adapter; avoid a second browser-side query engine. If the Python SDK cannot express a required query, add a tested upstream SDK method or isolate a temporary structured CLI adapter with explicit provenance rather than parsing prose output.

Keep experimental ECL as data, not dynamically generated Python. Arbitrary Python predicates, raw SQL, and user-authored code execution are outside the first slice. If later required, run them in a separate least-privilege process with explicit argv, staged read-only inputs, a scrubbed environment, no ambient credentials or network, resource and time limits, aggregate-only output, and cleanup on success or error. A marimo cell or run button is not isolation. The initial notebook must not rewrite application modules, submit results, mutate external state, or persist candidate data. It owns presentation and temporary orchestration; an application-specific adapter owns its schema and predicate.

## Trust, Privacy, And Licensing

Term and encounter content is shown only to an authorised local user. Default application-data views contain aggregates, not patient or encounter identifiers; terminology views still contain SCTIDs. Agent/pairing capabilities can inspect live variables, execute code, and manipulate the UI, so enable them only for explicitly authorised synthetic-data editor sessions. Running the notebook locally does not imply agent context remains local. A cloud-backed agent is a separate synthetic-only profile whose provider traffic and data policy are explicit. Private sessions run without editor or pairing capabilities.

Licensed terms, private rows, and sensitive paths must not appear in distributed notebook source, sample outputs, exports, snapshots, tracebacks, logs, agent context, audit records, or packaged widgets. A private-session launcher leaves every auto-download format unset, disables table downloads, redacts errors and provenance, hides client-side export affordances, and blocks snapshot/export routes at an outer policy boundary. Do not assume a global export-denial switch exists in the selected marimo release; verify its behaviour when pinning the dependency. These controls cannot prevent an authorised viewer from manually copying or capturing displayed data. A private session writes no licensed output to notebook source, runtime directories, caches, exports, logs, or audit records; in-memory state is discarded on shutdown.

The zero-egress profile uses bundled assets and preinstalled dependencies, disables update checks, and prohibits runtime package installation, pairing, remote AI providers, analytics, and remote terminology calls under an egress-denying outer boundary. Any external terminology adapter requires a separate use case, release policy, and rights decision. Distributed software remains AGPL-3.0-or-later; production SNOMED CT content and derived databases are separate licensed material and must not be bundled or redistributed unless their terminology licence permits it.

## Validation Slices

1. **Capability and concept lens:** on the committed upstream synthetic RF2 fixture, look up `22298006` (Myocardial infarction) and `46635009` (Type 1 diabetes mellitus), then run lexical search. Render stored terms, active state, release, and a display-bounded keyboard-operable parent/child inspector. Cross-check the same build through Rust SDK, Python SDK, and CLI. Confirm unavailable metadata/history differs from a loaded empty value and paths are redacted from exportable provenance.
2. **ECL scratchpad:** edit two expressions, mark prior results stale, then request expansion explicitly. Show exact concept-set additions/removals and clickable concept references with total/returned/truncated state. Compare SCTID sets to the Rust SDK for supported constructs. Surface grouped refinement and another unsupported construct as clear notebook-level errors, not silent sets. Verify parse/evaluation detail and annotation warnings cross the adapter boundary without process stderr. Never infer row impact from set counts alone.
3. **Hierarchy honesty:** exercise multiple direct parents, an over-limit child set, inferred attributes, and current associations. Verify the UI never presents one representative hierarchy path as the only lineage, flattened attributes as role-group-preserving definitions, a limit as complete pagination, or missing history evidence as no associations.
4. **Data bridge, later:** after `R87` resolves its contract, plug in a synthetic dataset and external read-only rule runner. Independently verify unique-row/encounter aggregation, duplicate policy, field and combined denominators, filters, matching/release provenance, and cleanup. The same fixture must give a deliberately different answer when the expression or rule changes.
5. **Trust and output boundaries:** use adversarial synthetic FSNs, preferred terms, queries, paths, and application values containing markup, quotes, controls, and newlines. Verify literal rendering; no interpolation into JavaScript, `innerHTML`, or inline handlers; no table download or persisted snapshot/export/cache/log/audit value; redacted tracebacks; and discarded in-memory state. Observe no external requests from browser, marimo process, or children under zero-egress. Confirm private sessions expose no pairing/editor capability and no private/licensed value reaches agent context. Test cloud-agent collaboration separately with synthetic data and authorised provider traffic.
6. **Human-agent usability and reuse:** with synthetic data, ask a clinician and agent to inspect and correct the same deliberately flawed expression and row rule. Measure whether the human can locate changed concepts and explain the changed aggregate without reading generated scripts. Compare this with the CLI workflow, then compare the inspector contract with shipped `R38` elements and choose reuse, adaptation, or separation for a measured reason.

## First-slice Acceptance

The first useful slice is one local marimo notebook that moves from an editable supported ECL query to a release-labelled, display-bounded exact set diff and accessible concept inspector; records a reproducible SDK invocation and available provenance; rejects grouped and unsupported semantics; has structured actionable errors; and retains or exports no licensed output. It passes validation slices 1, 2, 3, and 5 on synthetic data. Encounter testing, agent access to non-synthetic sessions, codelist persistence, Jupyter/DuckDB veneers, and component reuse remain separately gated.

## Reading And Prior Art

These are research leads, not implementation dependencies or endorsement. Read original material before borrowing UI ideas, code, or terminology content.

- [SNOMED International's translation notebook proof of concept](https://github.com/IHTSDO/snomed_translation_poc) - notebook-based concept sampling and relationship context, not evidence of a collaborative ECL/application workbench.
- [DrivenData SNOMED challenge resources](https://www.drivendata.org/competitions/258/competition-snomed-ct/page/823/) and [`snomed_graph`](https://github.com/VerataiLtd/snomed_graph) - sample notebook for browsing/selecting concepts; the graph library explicitly does not implement ECL.
- [Ontoserver ECL notebooks](https://github.com/sophie-w/ONTOSERVER_api) - Jupyter examples expanding ECL through a remote FHIR terminology server, in contrast to the proposed local `sct` backend.
- [ECLed: a tool supporting the effective use of SNOMED CT ECL](https://pmc.ncbi.nlm.nih.gov/articles/PMC12777381/) - ECL authoring, live results, MRCM guidance, and a parent/child concept viewer. Study its small usability survey and untested larger-dataset scalability rather than copying its separate architecture.
- [CSIRO Shrimp/ECL Builder](https://ontoserver-wp.csiro.au/our-solutions/shrimp/), [`aehrc/ecl-builder`](https://github.com/aehrc/ecl-builder), and [`aehrc/ecl-lsp`](https://github.com/aehrc/ecl-lsp) - direct ECL composition/editor prior art. Check their terminology-server assumptions; they are not semantic authority for `sct`.
- The current [SNOMED CT Expression Constraint Language specification](https://docs.snomed.org/snomed-ct-specifications/snomed-ct-expression-constraint-language) is semantic authority; implementation and editor prior art do not override it.
- [SNOMED International terminology services](https://www.implementation.snomed.org/terminology-services) and [SNOMED CT Browser ECL examples](https://docs.snomed.org/snomed-ct-user-guides/snomed-ct-browser-guide/tips-and-tricks/ecl-examples) provide reference jobs and an independent comparison point.
- [marimo documentation](https://docs.marimo.io/) covers editor inputs, tables, widgets, pairing, source watching, exports, and session snapshots. Treat them as candidate building blocks and trust boundaries, not a ready-made SNOMED integration, and reverify behaviour against the pinned release.
